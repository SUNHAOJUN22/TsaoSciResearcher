# TsaoScience astra-pro-2 integration contract

## One repository, domain-specific implementations

The canonical repository remains SUNHAOJUN22/TsaoSciResearcher. There is no submodule, dynamic external clone, duplicated runtime platform or destructive loss of source history. Domain algorithms, licensing and controlled classification retain their original boundaries. Seven component identities are derived from one components registry and checked against the immutable migration lock.

## Shared contracts and real reuse

The Aspen and Computation hashing entry points call tsao_science.core.hashing with their respective historical ensure_ascii policy. These compatibility hashes are not the typed-binary64 tsao.c14n/1 protocol. Cache parsing uses root strict JSON. Flow conversion and residual summation reject nonfinite results as well as nonfinite inputs.

Payload schemas cover the ten registered runtime capability declarations. Eight have local-reference execution and output schemas; two remain external hold. A task reference can defer validation only during planning. Resolved payloads and worker outputs must pass actual schemas before state propagation. Reference/hypothesis results cannot be relabeled measured or simulated. Control ordering alone is not treated as data provenance.

## Catalog versus execution

The catalog is derived from retained original metadata, not generated duplicate capability files. Current source counts are research 341, computation 164, aspen 15, DFT 12, processing 4, ResinDB 26 and reasoning 3, total 565. Entries retain original file digest and qualified identity. Historical descriptions and validation labels do not become executable qualifications. Runtime-local count remains 8.

## Result verification

run/2 binds workflow, task graph, resolved inputs, outputs, verdicts and provenance. Import verification is non-executing and checks self-consistency, not authenticity. An attacker able to replace a record and all hashes can create a different self-consistent record; no source authentication or scientific approval is claimed. Read-only ledger verification checks the recorded chain checkpoint and matching task events; later events do not invalidate an earlier verified checkpoint. The ledger is not an independent signed authority.

Legacy run/1 records retain digest verification but explicitly report missing workflow binding. They do not gain run/2 guarantees.

## Workbench

GET /api/science/status, /catalog, /capabilities, /contracts and /examples read the same registries. POST /plan and /verify validate only. Requests have content, host/origin, size, framing and time bounds; no solver execution or AI relay endpoint is introduced. The UI hashes and transmits one immutable workflow snapshot. Imported observations are displayed, not inserted into the measured-data database.

## Verification scope

The extended profile retains all original a1 regression stages and adds five groups of existing numerical and control-boundary regressions. Each run has a unique artifact directory, stage logs and parsed JUnit counts. Missing or malformed JUnit cannot yield a stage pass. The final CI job checks all required completed job results and binds its report to GitHub SHA, run and attempt.

Full inherited release, packaging, mutation, coverage, hardware and external-science qualification are not represented as executed by this profile. No threshold is lowered in an inherited gate. Source integrity checks run before and after tests. Processing public distribution remains blocked according to the original classification policy.

## Repository retirement

The six old repositories are redirect-only source-history references. Platform archive/delete require separately authorized repository administration. The provided local-owner tool defaults to read-only audit, never deletes, and verifies each archive through readback. Its presence is not evidence that archive was executed.
